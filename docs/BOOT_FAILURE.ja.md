# SEC001で起動しなくなった原因と、有線復旧で分かったこと

対象は所有する初代Q-SL1の1個体です。2026-11-01の無線切替後に起動音・BLE広告が出なくなり、2026-11-03にUARTで読み出しと復旧を行いました。この資料は、公開用に記録を整理した技術報告です。個体の全EEPROM、鍵、カード情報、アドレス、PCのパス、個体全体のハッシュ、未加工のログは含めていません。

**SEC001が停止した直接の命令・例外PCは特定できていません。SEC001の起動処理・RAM配置の変更に原因があるという推定を強める証拠はあります。一方、起動失敗後に無線で戻せなくなった設計上の原因と、投入前の検証不足は確認できています。**

## 観測した経緯

| 段階 | 記録から確認したこと |
| --- | --- |
| 純正1.4.01でstage | SEC001の26,972バイトを予備DS2へ転送して全体照合。純正DS1と起動選択を保持した状態で、純正の再起動・所有者認証に成功 |
| SEC001へactivate | 候補とSS2を照合し、SS1先頭を無効化。その後のBLE再接続で対象を検出できず停止 |
| 電池再投入・別ホストの確認 | 起動音が出ず、Pi・Windowsのいずれでも広告を検出できなかった |
| 11月3日、ROM UART | 標準HCIに応答。EEPROM全64KiBを独立に2回取得し、全バイトが一致 |
| 故障時データの比較 | 純正DS1は正常時と一致。SS1の残り39バイトも一致。DS2のSEC001は転送時の保存コピーと一致し、SS2も予定の参照と一致 |
| 最初のマーカー復元試行 | 書き込みACKは返ったが、先頭は00のまま、全EEPROMも不変。復旧成功とは扱っていない |
| WP設定を整えた有線操作 | 既存ROMのWPコールバックを一時登録し、ページごとの書き込み・全体照合が成功。純正DS1と所有者領域を保持 |
| 実証した起動復帰 | 既に起動実績のあった最小変更版DEV001をDS2へ配置・選択。配線を外して電池起動すると、音・ランプ・広告・版表示が復帰。既存鍵によるReadStatusも成功 |
| その後のSEC002 | 起動配置を変えない対策へ作り直し、有線導入と通常起動・既知経路拒否・所有者認証を1個体で確認。後にXIAO経由のHomeKit施錠も確認 |

上の比較から、故障時に保存されていたEEPROM内容について、転送候補との不一致は見つかりませんでした。転送が一致したことは、候補コードが正常起動できる証明にはなりません。

最初のACKだけの操作と、後続の有効なWP設定を使った復旧は別です。**単独の1バイト復元だけで純正の通常起動を確認した、という実機記録にはしていません。** 公開[有線キット](../wired/README.ja.md)も、この境界を検証範囲として明示しています。

## SEC001が変えていた起動処理

SEC001は、認証前の保守用通信を所有者認証へ結び付けるため、プロファイル初期化の呼び出しをフックし、L2CAPの通信テーブルを書き換えました。追加コード120バイトをRAM末尾へ置き、DSレコードと動的メモリの境界定数も変更しました。

```text
ROMが起動設定を選択 → DS2をRAMへロード
  → C起動処理・BSS初期化・動的メモリ境界の設定
  → BLEスタック／プロファイル初期化
  → SEC001で追加したテーブル操作
  → GPIO等の初期化 → BLE広告開始
```

追加処理は広告開始より前に実行される位置です。ここに不具合があれば、所有者認証を始めるための無線接続まで到達できません。ただし、当時の実機でフックの到達や停止アドレスを測定したわけではありません。[メーカーの起動順序の説明](https://community.infineon.com/t5/Smart-Bluetooth/How-image-is-validated-during-bootup/td-p/198938)も、アプリの初期化段階とイベント処理を区別しています。

### RAM境界に32バイトの差があった

取得済み起動コードのオフライン実行と、当時参照したSDKの計算規約を比較すると、常駐領域末尾へ32を加えて16バイト境界へ整列する規約に対し、候補は追加コードの末尾をそのまま使っていました。

| 項目 | 純正 | SEC001 |
| --- | --- | --- |
| 常駐領域／追加コードの末尾 | `0x20A11C` | `0x20A200` |
| 実際に設定される動的領域の開始 | `0x20A130` | `0x20A200` |
| 同じ計算規約を適用した値 | `0x20A130` | `0x20A220` |
| 規約との差 | 0 | 32バイト |

この差は確認しました。しかし、実際のアロケーターが追加コードへ書き込んだ記録や、停止時のレジスターはありません。**32バイト差が今回の停止原因だったとは断定できず、それだけ直せば起動するともしません。** メーカーも初期化後にRAMを再利用する構造を説明しており、末尾が空いて見えることだけでは常駐コードの安全な配置を証明できません。[メーカーのメモリー配置資料](https://community.infineon.com/t5/Knowledge-Base-Articles/BCM20732-Memory-Map-Architecture/ta-p/246756)

### テーブル参照の検査が足りなかった

SEC001のフックは、テーブルのポインターがゼロでないことだけを検査して参照していました。範囲・整列・行数の上限・目的の登録行が存在することを十分に検査していませんでした。

オフラインでは、正常な初期化済みテーブルなら処理できること、非ゼロの無効ポインターならアクセス例外になること、空の表を処理した後に対象通信が登録されると対策が付かないことを確認しました。いずれも**条件付きの反例**です。実機の初期化時ポインターは取得していないため、「テーブル未初期化が原因だった」とは結論しません。

## 純正が残っていたのに、なぜ無線で戻せなかったか

純正DS1はEEPROMに保持していましたが、activate時に純正SS1の先頭マーカーを01から00へ変え、SS2から候補を選ぶ状態へ切り替えました。候補が起動しなければ自動的にSS1を選び直す監視・ロールバックは実装していませんでした。

想定した無線復旧は、新しいファームのBLEと所有者認証を使う経路でした。新ファームが広告前に止まると、その経路へ接続できません。例外処理から復帰コマンドを送り直しても、無線の受信側自体が動いていなければ届きません。

**元のイメージを残すことに加えて、失敗したアプリに依存しない復旧経路が必要でした。** 今回、ROM UARTがその役割を果たしました。自動ロールバックを実装していなかった判断は、実装・投入側の問題です。

## 事前検証で見落としたこと

- 追加フックのエミュレーションでは、実際の`bleprofile_Init`を即時復帰へ置き換え、その中のメモリ操作を実行していなかった。
- 通信テーブルを初期化済みの人工データとして配置し、実ROMの確保・登録順を再現していなかった。
- 通常Dataレコード以外のB9レコードの意味・配置、割り込み、周辺回路、省電力復帰を再現していなかった。
- RAM境界を候補側が定めた定数と比較し、独立した配置規約との違いを見逃した。
- 表示文字列だけを変えたDEV001の転送・起動成功を、起動処理とRAM配置を変えたSEC001の安全性の根拠として扱った。
- 読み戻し一致、起動先の切替整合性、通常起動、故障後の復旧を、十分に別の確認項目として扱えていなかった。

保存したバイト列と一部の関数が期待どおりでも、実機の起動が確認できたことにはなりません。利用者の電池操作やカード入力を今回の起動障害の原因とする証拠はありません。

## SEC002と公開版で変えたこと

SEC002は使わなくなる既存OTA処理領域へ対策を収め、追加RAM・追加DSレコードを使わず、C起動処理・BSS末尾・動的メモリ境界を保持しました。通信テーブルの範囲・整列・件数を検査し、対策が確認できた場合だけ広告へ進みます。詳細は[セキュリティの範囲](../SECURITY.md)にあります。

この変更は自動復旧ではありません。SEC002は無線FWUと旧OTAを閉じるため、以後のファーム保守・起動障害の救済は有線です。起動フックを含む変更に「文鎮化しない」と保証はしません。

公開キットは正常時・故障時の暗号化バックアップと新しい直前読み出しを照合し、純正DS1とSS1が一致する場合のマーカー復元だけに絞りました。ACK、全体読み戻し、RAM設定の復元、配線を外した通常起動を区別します。現在稼働中の本体へ、公開版の復旧コマンドを再実行して検証したわけではありません。

## 公開した証拠と残る限界

[整理済みの観測一覧](evidence/SEC001.json)には、元記録から確認した数値・真偽値と、推定・未確認事項を収録しています。元記録は本人の手元にあり、公開データだけから実機の読み出しを再検証できる形ではありません。全ダンプや個体の識別子を公開する代わりの、証拠の要約です。

新しい有線ツールの合成試験は、バックアップ不一致・応答喪失・書込無効・対象外変更・保存失敗・後処理失敗を扱います。合成試験は実機起動の再現ではありません。SEC001の停止命令、32バイト差と障害の因果、別個体での動作、公開版復旧コマンドの実機通し試験は未解決・未実施です。失敗したSEC001の再配備ツールや純正コードは配布していません。
